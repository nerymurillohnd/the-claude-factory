# Debugging (only on request or to resolve a finding)

Read this only when the user named a specific problem or an audit finding needs it. Diagnosis never authorizes source changes or history rewrites.

If the user gave only a problem and no cleanup request, investigate it, deliver the finding in chat (what you found, the evidence, the commit or line, and what you could not verify), and ask whether they also want the cleanup. Run Phase 2 and 3 only if they do. If a cleanup is also wanted, finish the investigation first, then start at Phase 1.

- Find text: `git grep -n -e '<pattern>' -- <pathspec>` searches the current checkout; add a revision (`git grep -n -e '<pattern>' <rev> -- <pathspec>`) for history. A match shows presence, not cause. Scope the search so it cannot print secrets; the guard refuses secret-bearing paths. `git grep -n`, `git blame` and `git show <sha>` print content, so the guard asks the user to confirm each one: that is expected.
- Find who last changed known lines: `git blame -L <start>,<end> -- <path>`, then inspect that commit's diff and context (`git show <sha>`) before attributing a defect.
- Find the commit that introduced a regression with `git bisect` only when you have a known-good and a known-bad revision, a deterministic classifier, and an isolated checkout. Creating that checkout is a state change: ask the user to approve a short plan first (the temporary worktree `git worktree add <temp dir outside the repository> <revision>`, the bisect, and removing the worktree afterwards with `git worktree remove`), and run it as `prep` actions with IDs. Review the test command for side effects first, keep a log (`git bisect log`), classify each revision good, bad or skip, and always finish with `git bisect reset` and the worktree removal. Skipped revisions can leave several candidates, and a candidate is not a proven root cause until it matches the real symptom. `bisect start` and its steps raise a confirmation prompt.
