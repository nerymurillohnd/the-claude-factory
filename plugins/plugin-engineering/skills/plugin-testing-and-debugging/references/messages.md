## Command conventions

1. If the user has an exact message, search this file for it. Each message is listed under the stage that produces it, which is not always the command that was run: an install can fail because a marketplace is missing, so that message is under "Add a marketplace".
2. If there is no message, or the plugin loaded a different copy than expected, or an update changed nothing, use `loading.md` to find which source, settings scope or file on disk decided it.
3. Check the plugin's state before changing anything. Establish the cause from the message or the stage, apply the entry's one fix, and confirm with what the entry says you see once the fix works.
4. Messages show placeholders such as `<name>` where they name a plugin or marketplace.
5. A `hooks module not loaded` or `hooks module did not load` message means the plugin is a mod: use the mods troubleshooting page (https://code.claude.com/docs/en/plugins/mods/troubleshoot), not this skill. A mod's own tests run with `claude plugin test [directory]`: it runs every `.test.ts` and `.test.tsx` file under the directory (default: the current one), needs no session, sign-in or network, and exits 1 when a test fails.
6. For flags, fields and commands, use the plugin commands reference, the manifest reference and the marketplace reference. Run `claude plugin --help` to see which subcommands the installed version has, and `claude plugin <subcommand> --help` for a subcommand's full options.
7. Shared rules of the `claude plugin` shell commands (alias `claude plugins`): exit `0` on success and `1` on failure; `validate` adds `2` for an unexpected error, and `eval` adds its own codes. A `<plugin>` argument is `name` or `name@marketplace`; use the qualified form when two marketplaces offer the same name; `configure` takes only the qualified form. `--scope` takes `user`, `project` or `local` and names the settings file the command writes to; `update` also takes `managed`. The `plugin marketplace` subcommands use the same exit codes, and their `--scope` has no `-s` short form.
8. Many commands take `--json` for scripts (install, uninstall, enable, disable, update from v2.1.268; marketplace add, remove, update from v2.1.287). The result is one JSON object on the last line of stdout, with `command`, `outcome` (`ok` or `failed`) and `message`, plus `pluginId`, `scope`, `marketplace` or `failureCode` when they apply. Parse only that last line, because a marketplace-declared command can print ahead of it. A usage error, such as an invalid `--scope`, prints no result line and exits 1 with the reason on stderr. `marketplace add` and `remove` can print no result line for the reserved name `anthropic-plugin-directory`, so check the exit code.

Each entry: what the user sees, the cause, the fix, and what shows once it works.

## B1. Where `/plugin` runs

`/plugin` is typed inside a running Claude Code terminal session and opens an interactive panel.

- **`/plugin isn't available in this environment`**: typed where there is no terminal to draw the panel: `claude -p`, the Agent SDK, the desktop app's Code tab, the VS Code panel, claude.ai/code. In VS Code only a `/plugin` line with arguments gets this; `/plugin` or `/plugins` alone opens the Manage plugins dialog. Install from the surface instead: desktop app (local or SSH) and VS Code have their own tabs under Install a plugin; a cloud session has no plugin browser (see its tab for what it loads); in a terminal, run `claude` and type `/plugin`, or `claude plugin install <plugin>@<marketplace>`. Works when `/plugin` prints `✓ Installed <plugin>.` or the shell prints `Successfully installed plugin: <plugin>@<marketplace>`.
- **`zsh: no such file or directory: /plugin`** (Bash: `bash: /plugin: No such file or directory`): typed at a shell prompt. Run `claude`, then `/plugin install <plugin>@<marketplace>`; or from the shell, `claude plugin install <plugin>@<marketplace>`.
- **`The term '/plugin' is not recognized as the name of a cmdlet`**: typed in PowerShell. Same fix.
- **`claude: command not found` after `claude plugin ...`** (Windows: `'claude' is not recognized ...`): not the plugin command. Follow "Verify your PATH" in the install troubleshooting, then retry.
- **`Unknown command: /<name>`, `error: unknown command '<name>'`, `error: unknown option '<flag>'`**: a spelling that does not exist. Use instead:
  - `claude plugin add <source>` → `claude plugin marketplace add <source>`, or `claude plugin install <plugin>@<marketplace>`;
  - `claude plugin install <plugin> --project` → `claude plugin install <plugin>@<marketplace> --scope project`;
  - `/install <plugin>` → `/plugin install <plugin>@<marketplace>`;
  - `/plugin add <source>` (opens Discover) → `/plugin marketplace add <source>`;
  - `marketplace.anthropic.com` as a source → `anthropics/claude-plugins-official`.
  These do work: `claude plugins` (alias of `claude plugin`), `claude plugin remove` (alias of `uninstall`), `/plugins` and `/marketplace`.
- **What each `/plugin` form does** (interactive terminal only): `/plugin` and any unrecognized first word open Discover; `/plugin help`; `/plugin list`; `/plugin install` opens Discover; `/plugin install <plugin>` opens its details; `/plugin install <source>` with a path, URL or `owner/repo` reports marketplace not found and installs nothing; `/plugin install <plugin> --marketplace <source>` adds the marketplace after confirmation (v2.1.275); `/plugin manage` opens Installed; `/plugin stats` opens Stats where `/skill-doctor` is available; `/plugin enable|disable|uninstall <plugin>` acts in Installed; `/plugin configure <plugin>` opens the `userConfig` dialog or reports there is none; `/plugin validate <path>` prints the `claude plugin validate` report inline; `/plugin tag`; `/plugin marketplace add|list|update|remove`. The shell subcommands `init`, `update`, `details`, `prune`, `eval`, `eval init` and `test` have no session form.
- **`Plugin "<plugin>" is not installed in this project`**: `/plugin enable`, `disable`, `uninstall` or `configure` named a plugin not installed in the current project.

## B2. Add a marketplace

- **`Marketplace "claude-plugins-official" not found`**: the official marketplace is not registered yet. It registers itself at the first interactive terminal session, not through VS Code only, and not when a policy blocks it, when `CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL` is set, or after a failed attempt awaiting retry. `claude plugin` shell commands never register it. Fix: `/plugin marketplace add anthropics/claude-plugins-official`. Works: `Successfully added marketplace: claude-plugins-official`, and `/plugin marketplace list` shows it. The same string in the Errors tab means a plugin in settings names a marketplace not added.
- **`Marketplace "<name>" not found`**: `/plugin install <plugin>@<name>` names a marketplace not added; or `/plugin install <source>` with a path, URL or `owner/repo` (that form gives this message even for an added source; see "Add a marketplace and install in one command"). A name starting `claudeai-` is hosted on claude.ai: `claude plugin marketplace add --claudeai <name>`. Otherwise Claude Code has no index of names: ask whoever sent the line for the source (`owner/repo`, git URL or path), add it, and run the install again. Review a third-party plugin before installing. If already added, check spelling against `/plugin marketplace list`.
- **`Invalid marketplace source format. Try: owner/repo, https://..., or ./path`**: accepted forms are a GitHub `owner/repo`, an `https://` or `http://` URL, a `user@host:path` SSH URL, or a local path starting with `./`, `../`, `/` or `~`. A bare name or bare hostname matches none. Retype, e.g. `/plugin marketplace add anthropics/claude-plugins-official`. The form decides the source type: `owner/repo`, `owner/repo#ref` or `owner/repo@ref` is `github`; `user@host:path[.git][#ref]` is `git` over SSH; a URL ending in `.git[#ref]` or containing `/_git/` (Azure DevOps) is `git`; `https://github.com/owner/repo` or `https://gitlab.com/namespace/project` is `git` with `.git` appended (nested GitLab subgroups work); any other URL is `url`, fetched as a `marketplace.json` (append `.git` to clone instead); a path to a directory is `directory` and to a `.json` file is `file`, both read in place (on Windows `.\`, `..\` and `C:\` also work). For a host whose clone URLs lack `.git`, such as AWS CodeCommit, declare it as a git entry in `extraKnownMarketplaces`. A bare host such as `gitlab.example.com/team/plugins` fails as an invalid shorthand, and the message says to add `https://` or use a local path.
- **`'<source>' is not a valid GitHub owner/repo shorthand`**: a hostname or extra path segment, such as `github.com/owner/repo`. Use the full clone URL for any host, the `https://` URL of a hosted `marketplace.json`, or a local path, e.g. `/plugin marketplace add https://github.com/anthropics/claude-plugins-official.git`.
- **`Invalid git URL`**: unsupported protocol, or an address git could read as a different server or folder. Rewrite it as the text after the address says. `is blocked by enterprise policy` instead comes from organization settings (B7).
- **`Path does not exist: <path>`**: nothing at that path; relative paths resolve against the current directory. Run from the right directory or pass an absolute path. A directory must contain `.claude-plugin/marketplace.json`, or the path must be a `.json` file; another file gives `File path must point to a .json file (marketplace.json)`.
- **`Marketplace file not found at <path>/.claude-plugin/marketplace.json`** (`Failed to add marketplace: ...`): no catalog at the expected path. The owner puts the file at `.claude-plugin/marketplace.json` (or an accepted location) and re-adds; anyone else asks the owner for the exact source.
- **`Cannot add marketplace "<name>": Claude Code cannot install plugins from a marketplace with this name`**: the `name` in `marketplace.json` is not valid after `@`: only a-z, A-Z, digits, `.`, `_`, `-`, starting with a letter or digit (e.g. `_internal` fails). Owner renames it, e.g. `internal-tools`; others ask the owner. Before v2.1.295 this add was reported as successful.
- **`Cannot add marketplace "<name>": Claude Code reserves this name and cannot register a marketplace under it`**: the name is a member every JavaScript object has, such as `constructor`, `toString`, `valueOf`. A declaration under `extraKnownMarketplaces` fails the same way at startup, in the Errors tab. Rename. Before v2.1.296 it failed with an internal error.
- **`SSH authentication failed` or `HTTPS authentication failed`** after `Failed to clone marketplace repository:`: first check the repository (misspelled, missing, or private without access): open it in a browser or run `git ls-remote <url>`. If it is right, the cause is credentials: Claude Code disables git prompts and askpass (including `GIT_ASKPASS`) and runs SSH in batch mode, so errors include `fatal: Cannot prompt because user interactivity has been disabled`, `terminal prompts disabled` or `fatal: unable to get password from user`. SSH: `ssh -T git@<host>` must succeed without a passphrase prompt and the host must be in `known_hosts`. HTTPS: the credential helper must hold a token; for GitHub run `gh auth login` and `gh auth setup-git`; test with `GIT_ASKPASS` unset and `git -c core.askPass= ls-remote <url>`. Then retry. Works: `Successfully added marketplace: <name>`, or for updates `Successfully updated marketplace: <name>` (shell) / `✔ Updated 1 marketplace` (session). `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` makes GitHub `owner/repo` sources skip SSH; otherwise SSH is used when a `github.com` key looks configured, with HTTPS fallback.
- **`SSH host key is not in your known_hosts file`** (or `SSH host key has changed` with a `ssh-keygen -R <host>` hint): clones use `StrictHostKeyChecking=yes`. Connect once to accept the key, e.g. `ssh -T git@github.com`, then retry; for a public repository, add it by `https://` URL instead.
- **`Command 'git' not found or is in an unsafe location (current directory)`** on Windows: install Git for Windows, open a new terminal, confirm `git --version`, and retry the add.
- **`Git clone timed out after 120s`**: raise `CLAUDE_CODE_PLUGIN_GIT_TIMEOUT_MS` (milliseconds, e.g. `export CLAUDE_CODE_PLUGIN_GIT_TIMEOUT_MS=300000`, or `$env:CLAUDE_CODE_PLUGIN_GIT_TIMEOUT_MS = "300000"`) and retry in that shell. For a monorepo, use `claude plugin marketplace add <source> --sparse <paths>`. For large submodules, update Claude Code: v2.1.295 and later fetch only submodules that hold plugin files.
- **Marketplace updates keep failing offline**: the existing checkout stays; each session the background check fails and tries a re-clone that fails too. Set `CLAUDE_CODE_PLUGIN_KEEP_MARKETPLACE_ON_FAILURE=1` to skip the re-clone for a checkout that already has `.claude-plugin/marketplace.json` (a never-cloned or partial one still tries; add it once while online). For fully offline deployments, pre-populate with `CLAUDE_CODE_PLUGIN_SEED_DIR` at image build time.
- **`Marketplace '<name>' already on disk — declared in <scope> settings`** after `claude plugin marketplace add`: not an error, exit 0. A successful add prints `Successfully added marketplace: <name> (declared in <scope> settings)`, using the name from the marketplace's own manifest. `--scope` (`user`, `project`, `local`; default `user`) picks the settings file; `--sparse <paths...>` limits the checkout (`github` and `git` only); with `--claudeai` (v2.1.273) the argument is a claude.ai marketplace name, and `--scope` and `--sparse` are refused. After an add, Claude Code installs dependencies that installed plugins were missing.
- **`Marketplace '<name>' is not declared in project settings. Omit --scope to remove it from all scopes.`** from `claude plugin marketplace remove --scope ...`: that settings file does not declare it. `<name>` is the name `marketplace list` shows, not the source. Removing a marketplace from its last declaring scope deletes its cache and uninstalls every plugin installed from it, with their options, secrets and data; the output lists them after `Also uninstalled N plugins from this marketplace:`. To refresh without losing plugins, use `claude plugin marketplace update` instead.
- **`claude plugin marketplace update` with `--json` and no name** refuses and exits 1. With a name it prints `Successfully updated marketplace: <name>`; without one, a count such as `Successfully updated 2 marketplaces`. A marketplace added with a branch or tag `ref` updates to the latest commit of that ref.
- **Add fails on a GitHub Enterprise Server host**: a policy error means an admin must add a `hostPattern` for the host; a GitHub access error on claude.ai means the user's GHES account is not connected. Both are on the GHES page.

## B3. Install a plugin

- **`Plugin "<name>" not found in marketplace "<marketplace>"`**: the name is not in the local copy of that catalog. In the shell it also appears when the marketplace was never added; if `claude plugin marketplace update <marketplace>` then says `Marketplace '<marketplace>' not found`, add it first.
  - With a refresh hint (`Your local copy may be out of date — try claude plugin marketplace update <marketplace>` or `The marketplace couldn't be refreshed (...)`): the catalog may be stale. Run `/plugin marketplace update <marketplace>` (works: `✔ Updated 1 marketplace`, or `Successfully updated marketplace: <name>`), then install again. If it repeats, check the name.
  - With no hint: the name is likeliest wrong. Copy it from Discover in `/plugin`. Before v2.1.232 the refresh ran only after the lookup missed and only with auto-update on.
- **`Plugin "<name>" not found in any marketplace`** (shell: `... in any configured marketplace`): no marketplace was named, and without one the shell searches cached catalogs only and `/plugin` refreshes only auto-update marketplaces. Name it: `/plugin install <name>@<marketplace>`. Works: `✓ Installed <plugin>.` or `Successfully installed plugin: ...`. If unsure which marketplace, check `/plugin marketplace list` and browse Discover.
- **`Plugin '<name>@<marketplace>' is already installed globally`** with `Use '/plugin' to manage existing plugins.`: already at user scope or by managed settings (`globally` is omitted without `@<marketplace>`). Nothing to add; change scope, enablement or config in `/plugin` Installed. A project- or local-only install does not trigger it. The shell prints `Plugin "<name>@<marketplace>" is already installed (scope: user)` and exits 0, and re-downloads if the cache directory is missing.
- **`"<plugin>" was not installed: it would share its folder with "<other>"`** (or `would share its saved data with`): the two ids map to the same folder once `.` and `@` become `-`, and on macOS and Windows ids that differ only in case collide too. If the other plugin is installed, the message says `Only one of the two can be installed.` and names the uninstall to run; run it, then install. If both arrive in one install (e.g. a plugin and its dependency), only a marketplace maintainer can fix it by renaming one.
- **`This plugin uses a source type your Claude Code version does not support`** with `Update Claude Code and try again.`: update, then retry.
- **`Plugin archive integrity check failed`** with `The archive was not installed.`: the downloaded file's digest does not match the entry's `sha256` pin. Publisher: recompute the digest of the exact file the URL serves (`shasum -a 256 my-plugin.zip`, or `Get-FileHash -Algorithm SHA256 my-plugin.zip`) and update the entry. Installer: `/plugin marketplace update <name>`, retry; if still mismatched, ask the owner which file they pinned before installing.
- **`An npm plugin source must name a registry package`**: the entry's `package` was refused before fetching, e.g. `"github:acme/formatter" was not installed: it is not an http or https link. ...`. The owner changes `package` to a registry package name, `name@version`, or a tarball link, or switches to a `github`, `url` or `git-subdir` source; others report it to the owner.
- **`Marketplace "<name>" is registered from an untrusted source`**: the name is reserved for official Anthropic marketplaces but the source is not a `github.com/anthropics/` repository; re-checked on every load, so it and its plugins stopped loading. User: `claude plugin marketplace remove <name>`, then add it from the official repository. Third-party publisher who used the name before it was reserved: rename and ask users to re-add. Before v2.1.205 the name was checked only at add time.
- **`Marketplace "<name>" is added but ignored`**: its `known_marketplaces.json` entry failed a check run on every read; `claude plugin list` prints the reason and fix (the Errors tab shows the fix on the next line). Reasons: location on a network drive, with `.` or `..`, or not checkable (also phrased about `The folder or file it was added from`); `Its git URL can't be used: <reason>` or `Its URL can't be read as an https:// or http:// address`; `Its source doesn't match its extraKnownMarketplaces entry in user or managed settings`; `(see the debug log)` instead of a reason means the name is refused, such as another spelling of a reserved name. Fix: follow the message; `claude plugin marketplace remove <name>` (works on an ignored entry, and uninstalls its plugins), add it again from a supported source or a local path, reinstall the plugins. To keep a network location, declare it under `extraKnownMarketplaces` in user or managed settings (a repository's settings do not count). For a source mismatch, re-add from the declared source or change the declaration. For a refused name, remove it (using the command after `Remove it:` when given); re-adding under the same name is refused again. Before v2.1.286 it was reported as `Marketplace <name> not found` or `... is registered but was refused (see the debug log)`.
- **`Plugin <name> has a corrupt manifest file`** (`JSON parse error:`: not valid JSON) **or `has an invalid manifest file`** (`Validation errors:`: fails the schema, e.g. `name: Invalid input`): in the shell the `<name>` can be a temp directory; the `Failed to install plugin "<name>@<marketplace>":` prefix has the real name, exit 1. The author fixes it: `claude plugin validate <plugin-directory>` shows the error with its path. Others report it.
- **`Plugin directory not found at path: <path>`**: the entry's relative path has no directory in the marketplace. Maintainer corrects `source` or restores the folder; others report it. **`Marketplace directory not found at path: <path>`**: the local marketplace's own directory moved or was deleted; restore it, or remove and re-add from the new location.
- **`No plugins available`** (empty Discover) **or `No marketplaces configured`**: no marketplace registered. `/plugin marketplace add anthropics/claude-plugins-official`. Works: `Successfully added marketplace: claude-plugins-official` and Discover lists plugins.
- **`Marketplace "<name>" is already added from a different source`** after `--marketplace <source>` on an install: the existing marketplace is kept and nothing installs, e.g. `... (github:acme/plugins). To use this source instead, remove that marketplace first with /plugin marketplace remove acme-tools.` Keep the existing one with `/plugin install <plugin>@<name>`, or remove it and retry with the new source.
- **`Cannot add marketplace "<name>": its source doesn't match its extraKnownMarketplaces entry in user or managed settings`**: sources match only with the same type and every field equal; an entry `ref` not passed, or an `https://github.com/` URL against a `github` entry (recorded as `git`), counts as different. Run `/plugin marketplace list` first: declared marketplaces register on their own. If it is not listed, add it typed as the entry writes it, e.g. for `{ "source": "github", "repo": "acme-corp/claude-plugins", "ref": "v1.2.0" }` run `/plugin marketplace add acme-corp/claude-plugins#v1.2.0`. To use a new source, edit or remove the entry (managed: ask the administrator). Before v2.1.287 the message read `... its network source differs from the one declared for it in settings (...)`.
- **`Failed to install: <plugin> (<reason>)`** from the `/plugin` menu: fix what the reason names. If shortened (the summary ends `Installing a plugin from its details (Enter) in /plugin shows its full error.`), select the plugin on Discover and press Enter to see the whole error.
- **`Could not move the new copy of this plugin version into <path>`**: the move into the cache failed, usually because another program (often a scanner) used the folder; the file-system code is in parentheses. The message says what happened to the previous copy: `The previously installed copy was moved back` (still installed); `had to be removed first`, `was not moved back` or `could not be moved back` (not installed until an install succeeds); no such sentence (no earlier copy). On Windows, `could not be replaced` with `It was not replaced and the new copy was discarded` means the old version is still installed. A `Left on disk` list is cleaned up later; do not delete it. Fix: close other sessions, editors and terminals using the folder under `~/.claude/plugins/cache`, then reinstall; if it says to check permissions, restore write permission on the named folder and free disk space.
- **Install outcomes from the shell**: `claude plugin install <plugin>` (`i`) defaults to `--scope user`. `Successfully installed plugin: <plugin>@<marketplace> (scope: <scope>)` is success. `Plugin "<plugin>@<marketplace>" is already installed (scope: <scope>)` exits 0. For a plugin whose entry runs a command or sets a `headersHelper`, it prints the command and asks `Run this command now? [y/N]`: declining prints `Aborted.` (command source) or `Aborted — the command was not run.` (`headersHelper`, or no TTY to confirm), exit 1. Without a TTY and without `-y` or `--accept-command`, the install is refused, says the command was only displayed, and exits 1. When Claude runs the install through its Bash tool, `-y` is ignored: the user must run it from their own terminal. `--config <key=value>` sets a `userConfig` option per flag (`<server>.<key>` for a bundled MCP server, v2.1.285). `--marketplace <source>` installs a bare name from that source, adding it first (v2.1.292).
- **A `--json` install that displayed a command and did not run it** returns `failed` with a `shownCommand` object (the command, the plugin, its `sha256`). The user accepts exactly that command by rerunning from their own terminal with `--accept-command <sha256>` (v2.1.271; no effect inside a session; not combinable with `-y`). The `sha256` stops matching if the command, the plugin or the catalog changed, including through the run's own refresh; `shownCommand.acceptCommandMatched: false` means review the command now displayed before accepting.
- **Dependency errors** (at install as the error message, or at load in `claude plugin list` and the Errors tab, with the plugin kept disabled):
  - `Dependency "<dep>" is not installed`: `claude plugin install <dep>@<marketplace>`, or uninstall the plugin. If the dependency's marketplace is not registered, add it and run `/reload-plugins`, which installs what it can resolve.
  - `"<name>@synced" is loaded from your claude.ai account but meets a marketplace dependency only for other claude.ai plugins` (inside `is not installed`): install the dependency from its marketplace; that copy then loads instead.
  - `Dependency "<dep>" is disabled`: enable it, or uninstall the dependent plugin.
  - `Requires "<dep>" <range>, installed <version>`: update the dependency into the range, or uninstall the plugin.
  - `... has conflicting version requirements`: uninstall or update one conflicting plugin, or ask upstream to widen its range.
  - `... has version requirements too complex to intersect` or `has an invalid version requirement`: fix the invalid range or simplify long `||` chains.
  - `... has no git tag satisfying <range>`: check upstream tags releases as `<name>--v*`, or relax the range.
  - `Dependency "<dep>" (required by <plugin>) is in marketplace "<marketplace>", which is not in the allowlist`: cross-marketplace resolution is off by default; install the dependency yourself at the same `--scope`, then retry.
  - `claude plugin list --json` shows `errors` and `errorDetails` with `type` `dependency-unsatisfied` (first three) or `dependency-version-unsatisfied` (the fourth).

## B3b. Enable, disable, update, uninstall, configure

- **`Plugin "<plugin>" is already enabled`** or **`... is already disabled`**: exit 1. With `--json`, `failureCode: "already_in_goal_state"` and `alreadyInGoalState: true`, so a script can treat it as success.
- **Scope for `enable` and `disable`**: without `--scope`, the first of local, project, user that mentions the plugin. A `--scope` with higher precedence than the declaring one writes an override there (e.g. `claude plugin disable formatter --scope local` turns off a project-enabled plugin for the user alone). Any other scope fails with `Plugin "formatter" is installed at project scope, not user. Use --scope project or omit --scope to auto-detect.` Success prints `Successfully enabled plugin: <name> (scope: <scope>)` or `Successfully disabled plugin: ...`.
- **`enable` fails on dependencies**: a dependency not installed (prints the `claude plugin install` command for each), blocked by organization policy (names it), or set to `false` at a higher-precedence scope (enable it there, or pass `--scope`).
- **`disable` fails**: with neither a name nor `--all`, `Please specify a plugin name or use --all to disable all plugins`, exit 1; `--all` cannot combine with a name or `--scope`. It fails when another enabled plugin depends on it (names the dependents to disable first) or when the organization requires it as a synced plugin (saves nothing).
- **`update`**: prints `Checking for updates for plugin "<plugin>"…` then the result; `<name> is already at the latest version (<version>).` exits 0. Without `--scope`, it updates the most specific installed scope for the current project: local, project, user, then managed. Before v2.1.281 it used `user`, so a project- or local-only plugin failed with `Plugin "<name>" is not installed at scope user`; pass `--scope` there. A bare name shared by plugins from different marketplaces is refused with the qualified commands to run (bare names from v2.1.246). At the latest version it can retry an unfinished dependency install; a failed retry prints `Failed to update plugin "<plugin>"` with the reason and exits 1 (before v2.1.287 there was no retry). A command-source plugin with a changed command needs `-y` or `--accept-command` without a TTY. The new version loads in the next session or after `/reload-plugins`.
- **`uninstall`** (`remove`, `rm`; default `--scope user`): `Successfully uninstalled plugin: <name> (scope: <scope>)`. A plugin not installed at that scope prints `Failed to uninstall plugin "<plugin>":` and exits 1. If it continues with `"<name>" was not uninstalled:` and names a settings file, Claude Code could not confirm the scope's settings no longer turn it on, so it stays installed; `--json` gives `failureCode: "settings_still_on"` (v2.1.282). Uninstalling from the last scope deletes its stored options, secrets and `~/.claude/plugins/data/<id>/`, except with `--keep-data`, when another plugin uses the same folder (ids that differ only in case), or when the install list cannot be read back (`savedKept: "install_records_unreadable"`, v2.1.282). `keptData` reports whether the data stayed; `/plugin` shows `· data preserved`. `--prune` also removes auto-installed dependencies nothing needs, and needs `-y` without a TTY; it cannot combine with `--json`.
- **`configure`** (v2.1.285; full `name@marketplace` only): without flags, lists each option as `required` or `optional`, `sensitive`, and `set` or `not set`, with no values. `--json` adds `schema`, `choices`, starting `inputs`, `configured` and `unconfigured`, with values of non-sensitive options only. `--values-stdin` saves a JSON object of single-line strings, e.g. `claude plugin configure formatter@my-marketplace --values-stdin < values.json`, and prints `Configuration saved. Restart Claude Code to apply it.` An undeclared key or an invalid value saves nothing: `Failed to save configuration:` with the reason, exit 1 (`--json`: a `refused` field with `message` and `option`). `No installed plugin has the id "<plugin>".` means no loaded plugin has that id.

## B4. Installed but not working

### Plugin does not appear or its skills do not show up

Check the state before changing anything:

1. `/plugin`, Installed: listed and enabled? `claude plugin list` shows version, scope and `Status: ✔ enabled`.
2. The Errors tab: each entry is a message plus guidance; most messages below come from it.
3. Installed during this session and error-free: `/reload-plugins`. It prints `Reloaded:` with counts of plugins, skills, agents, hooks and servers, and `N errors during load. Run /plugin for details.` when something failed.
4. Loads with no error and still no skills: for the user's own plugin, see B5 "Plugin loads but its skills are missing"; for someone else's, open its details pane in Installed; a plugin that lists no skills has none.

### Messages

- **`Run /reload-plugins to apply.`** (instead of `Plugin is now active.`, possibly with `Plugins changed. Run /reload-plugins to activate.`): activation was deferred because it would invalidate the prompt cache or failed. The panel runs `/reload-plugins` itself or queues it. Read the result: `Reloaded:` with counts means active; `This reload changes MCP tools (...) ... Run /reload-plugins --force to apply.` (or `This reload adds/removes the LSP tool`) means run `/reload-plugins --force` or start a new session. Before v2.1.268 the install stayed pending until a manual reload; before v2.1.246 the skills count included only `commands/` entries.
- **`The packages it lists are not installed`**: the dependency install can run but did not finish. Run the `claude plugin update` the note gives (e.g. `claude plugin update formatter@my-marketplace`) or update from `/plugin`; a failed retry prints the cause. With `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` set, the retry is skipped. **`were not installed, because ...`**: it cannot run, for the named reason (Yarn, pnpm or `bun.lockb` lockfile: the author must replace it; a missing package manager: install it, then update).
- **`Plugin "<name>" not cached at <path>`** with `Run /plugin to refresh the plugin cache`: no usable copy, e.g. the cache was cleared, or a repository enables a plugin not installed. For a repository's plugin: `claude plugin install <name>@<marketplace> --scope project` from the project. Otherwise `claude plugin install <name>@<marketplace>`, which re-downloads a missing install directory. Then `/reload-plugins`. Works: the Errors entry is gone and Installed lists it.
- **`installed_plugins.json holds a record under "<id>" that this version of Claude Code cannot read`** (as a `Note:` in `claude plugin list`; as `Plugin "<name>" was not installed/uninstalled/updated:` on those commands; `failureCode: "install_records_unreadable"` with `--json`; `holds records under` for several; `installed_plugins.json is in a format (version <N>) that this version of Claude Code does not know` for the whole file): most likely written by another, newer version. The file is not rewritten while it is there. In order: `claude update`; if impossible, uninstall the plugin with the version that wrote it; if neither helps, delete the record by hand, then restart or `/reload-plugins`.
- **`installed_plugins.json could not be read and was rebuilt`** with a `installed_plugins.unreadable.<date>.<hash>.kept` path: the file was not valid JSON or not a list. Open the `.kept` file to see what it recorded and reinstall what is missing. It is never read back and ages out.
- **`install records under names that no version of Claude Code can use were removed from installed_plugins.json`** with a `.set-aside` copy, ending `Nothing needs doing about these copies.`: records under invalid ids were dropped; the rest loads normally. Nothing to do.
- **`does not load (...), so Claude Code ignores the whole file`** after a successful `install`, `enable`, `disable` or `marketplace add`, e.g. `⚠ /home/user/.claude/settings.json does not load (its "permissions" is not valid), ...`: the command worked but the named settings file has an error, so the whole file, including the command's change, is ignored. `its "<key>" is not valid` (or `and N other value are not valid`): look the setting up in the settings reference. `it is not a JSON object`: the top level is not an object. Fix the file ("Fix a broken settings file"), then rerun the command if its change is missing. If a newer Claude Code wrote the file, update instead.
- **`Disabled in ~/.claude/settings.json but still loads`**: a higher source enables it (A3). To opt out of a project-enabled plugin, set `false` in `.claude/settings.local.json`. If marked `required by your org`, no settings file is involved: the organization requires that synced plugin.
- **`Plugin "<name>" is enabled in project settings but isn't installed here`** with `Run claude plugin install <name>@<marketplace> --scope project to install it for this project`: repository settings enable but do not install, and an external source is not downloaded until installed. Run the command from the guidance, then `/reload-plugins`. Works: entry gone, plugin under Installed. Organization pre-installs go through managed settings instead.
- **A plugin stays installed after `plugin uninstall` on Windows** (project or local scope): two records spell the folder path differently (check `projectPath` in `claude plugin list --json`, e.g. `c:\work\app` vs `C:\work\app`). Run the same uninstall again with the same `--scope` from the same folder, e.g. `claude plugin uninstall <name>@<marketplace> --scope project`, then confirm with `claude plugin list --json`. Before v2.1.295 the second run fails with `Plugin "<name>" is not installed in project scope`; run `claude update` first.
- **A git-sourced plugin shows `Version: unknown`**: the commit could not be read. 1. `claude update` (v2.1.302 or later clones in a readable format). 2. `claude plugin marketplace update <marketplace>`. 3. `claude plugin update <name>@<marketplace>`. 4. `claude plugin list` should show a 12-character commit ID. `update` changes one scope per run; for a block still `unknown`, rerun with its `--scope`. If still `unknown`, see "Get more help".

### Hooks that do not load, fail, block or never fire

- **Hooks fail to load** (Errors tab):
  - `Failed to load hooks from <path>: <reason>`: `hooks/hooks.json` is not valid JSON or fails the schema. Fix it; `claude plugin validate <plugin-directory>` catches JSON syntax before publishing.
  - `hooks path not found: <path>`: the manifest's `hooks` names a missing file. Fix the path or add the file.
  - `hooks path escapes plugin directory: <path>`: see A4 "Paths that escape the plugin directory".
- **`... hook error: Failed with non-blocking status code: <stderr>`**: the hook ran and its command failed, e.g. `Stop hook error: Failed with non-blocking status code: /bin/sh: node: command not found` (install `node` or put it on the `PATH` of the terminal that starts `claude`). If the stderr shows the plugin path cut at a space, a shell-form command uses `${CLAUDE_PLUGIN_ROOT}` unquoted and the path has a space: wrap it in double quotes or use exec form; `claude plugin validate` shows a quoting warning. `Failed to run: Plugin directory does not exist: <path>`: see below. For anything else, run the hook's command yourself from the plugin directory, or capture stderr with debug logging.
- **A hook blocks a tool call or prompt**: it exited with code 2. The error ends `This hook comes from the <plugin> plugin.` (v2.1.281 or later), naming which plugin to disable or fix. A path cut at a space: the unquoted-variable fix above.
- **A hook loads but never fires**: open the plugin's details in `/plugin`. `Its hooks.json hooks do not run` means a same-named plugin registered its hooks (A6). Otherwise: 1. check the event name, which is case-sensitive (`PostToolUse`); 2. check the `matcher` matches the tool name; 3. trigger the event on purpose (for `PostToolUse`, ask Claude to edit a file); 4. read the debug log, which records which hooks matched and their exit codes.
- **A hook runs twice**: hooks have no prefix, so a hook that is in both a settings file and a plugin's `hooks/hooks.json` runs twice each time its event fires. It typically happens after packaging a `.claude/` setup into a plugin while the hooks object is still in `settings.json`; remove it there once the plugin carries it. When an event fires, all its matching hooks run in parallel, so a plugin's `PreToolUse` hook and the user's own both fire. Sources: "Create plugins" (https://code.claude.com/docs/en/plugins/create) and "Hooks reference" (https://code.claude.com/docs/en/hooks).
- **`Failed to run: Plugin directory does not exist: <path> (<plugin> — run /plugin to reinstall)`**: the directory the session loaded the hooks from is gone. Run `/reload-plugins` first, even though it says reinstall. The failure shows once per session per event and command, so silence does not confirm the fix; read the reload: `Reloaded:` with no errors line (fixed); `N errors during load...` (follow the Errors tab entry); a line ending `Run /reload-plugins --force to apply.` (nothing reloaded; run it with `--force`). Different from `Plugin directory not found at path` (a marketplace entry, B3).

### MCP servers

- **`Invalid MCP server config for "<server>": <error>`**: the config passes the schema but cannot be resolved for this session. `Missing environment variables: <names>`: set them in the shell that starts Claude Code, then a new session. `URL is unset or invalid`: a `${user_config.*}` the URL uses is unset; `/plugin configure <plugin>`. `has an invalid MCP url` or `headersHelper for MCP server '<server>' references ${user_config.*}`: the plugin's own MCP configuration is wrong; fix `url` or `headersHelper`, or report it to the author.
- **`Bundled MCP server "<name>" was not started: it needs configuration`**: an MCPB bundle's required `user_config` value is missing or invalid; the rest of the plugin works. Installed tab, select the plugin, Configure; after `Configuration saved.` the reload starts the server. Before v2.1.285 the server was skipped silently.
- **Configured but never connects**: `/mcp` shows status (connected when healthy). For the startup error, `claude --debug` and open `~/.claude/debug/<session-id>.txt` (`--debug` prints nothing to the terminal). If a stdio server's connection failed less than 15 minutes before, it is not started in the new session: Reconnect from `/mcp`, then read the log. A `.mcp.json` entry that fails the schema is dropped and logged only in the debug log as `Invalid MCP server config for <server> in <path>`; `claude plugin validate` reports it as an error (since v2.1.281).
- **Works with `--plugin-dir`, fails after install**: the installed copy lives in the cache, so source-only paths break. Write paths inside the plugin with `${CLAUDE_PLUGIN_ROOT}`. For paths outside the plugin, see B5.

### Language servers

- **Does not start**: the binary is installed separately and spawned by name from `PATH`. The Errors tab shows e.g. `Executable not found in $PATH: "<binary>"`; `claude --debug` logs `LSP server <name> failed to start: <reason>`. Install the binary, confirm with e.g. `which typescript-language-server` in the terminal that starts `claude`, then a new session.
- **Too much memory** (e.g. `rust-analyzer`, `pyright` index the whole project): `/plugin disable <plugin>` and rely on Claude's built-in search.
- **False positives in a monorepo**: the server is not configured for the workspace. Nothing to fix in Claude Code; it does not stop editing.

## B5. Build a plugin

While developing with `--plugin-dir` or a local marketplace. Hooks that do not fire and MCP servers that do not start are in B4.

- **`commands path not found: <path>`** (also `skills`, `agents`, `hooks`) with `Check that the path in your manifest or marketplace config is correct`: a path resolved against the plugin root found nothing; the message shows the absolute path checked. Compare with the disk, fix the path or create the directory, then `/reload-plugins`. Manifest paths are relative to the root and start with `./`; one that resolves outside is `<component> path escapes plugin directory` and is dropped. Before v2.1.299 the message could appear at startup on a `synced[0]` row when another session had just updated a synced plugin; restart, or update to v2.1.299.
- **`--plugin-dir` at a marketplace root does not load plugins under `plugins/`**, with no error: `--plugin-dir` takes the plugin root (with `.claude-plugin/plugin.json`); `marketplace.json` is not read. Point at the plugin: `claude --plugin-dir ./my-marketplace/plugins/my-plugin`, then check its details in Installed. Before v2.1.281 a marketplace root loaded as one empty plugin.
- **Files referenced outside the plugin directory are not found** after install (e.g. `../shared-utils`): the cached copy has nothing outside the plugin. Move the shared files inside, or reference them through a symlink inside the plugin.
- **`${CLAUDE_PLUGIN_ROOT}` shows forward slashes on Windows** (`C:/Users/you/...`): shell-form hooks run through Git Bash by default and get forward slashes, which Bash builtins, MSYS tools and Windows binaries accept. If a script needs backslashes, use an exec-form hook with an `args` array, or `"shell": "powershell"`.
- **Plugin loads but its skills are missing**: skills load from `skills/` and commands from `commands/` at the plugin root; only `plugin.json` belongs in `.claude-plugin/`, and `skills/` inside it is not scanned. Move the directories to the root and `/reload-plugins`; the details pane then lists the skills. Each skill is a directory with `SKILL.md`; a `skills` entry pointing at the file gives `path is a file; skills entries must be directories containing SKILL.md`.
- **Skill runs as `/<plugin>:<skill>` but Claude never invokes it**: in order: `disable-model-invocation: true` (the template in Create your first plugin sets it; remove it); the description does not match how people ask (Skill not triggering); the description is truncated because many skills are installed (Skill descriptions are cut short). To measure triggering, write an eval case with a `tool_used: Skill` grader and run `claude plugin eval` after each description change.
- **`<directory> is not a plugin or skill folder`** from `claude plugin eval init`: run from the plugin root (with `.claude-plugin/plugin.json` or the skill's `SKILL.md`), or pass `--eval-dir` to scaffold elsewhere on purpose.
- **The `userConfig` dialog never appears**: it appears with `/plugin install` or the Discover tab; the VS Code Manage plugins dialog asks for unset options after install (before v2.1.285 it did not; use `/plugin configure <plugin>@<marketplace>` from a terminal); `claude plugin install` never prompts, saves `--config KEY=VALUE` values, and prints `N userConfig options not yet set — run /plugin configure <plugin>@<marketplace> in Claude Code, or pass --config KEY=VALUE.` (with `(M required)` when any are required). Pass one `--config` per option, e.g. `claude plugin install my-plugin@my-marketplace --config api_url=https://example.com`; with all set there is no `not yet set` line. Or open the dialog later with `/plugin configure my-plugin@my-marketplace`, or use `claude plugin configure` from the shell (v2.1.285), which shows unset options and reads values from stdin. An undeclared key installs anyway with `⚠ Installed, but --config not applied: --config key "<key>" isn't declared in this plugin's userConfig.` and the declared keys; with an MCPB bundle declaring `user_config`, the message adds `or by its bundled MCP servers.` and lists `<server>.<key>` keys (v2.1.285); a bundle referenced by URL is not read at install, so configure it in `/plugin`.
- **`claude plugin validate` reports errors** (`Found N errors`, `Validation failed`, exit 1; also `/plugin validate <path>`): it reads `.claude-plugin/plugin.json` for a plugin directory, `.claude-plugin/marketplace.json` for a marketplace, both when both exist (before v2.1.289, the marketplace alone). Entry problems are prefixed `plugins[1] plugin.json → json: ...`. Messages:
  - `File not found: <path>`: run against the root that contains `.claude-plugin/`.
  - `No manifest found in directory. Expected .claude-plugin/marketplace.json or .claude-plugin/plugin.json`: create the manifest or point at the right directory.
  - `Invalid JSON syntax: <parse error>`: fix the JSON. Until `hooks/hooks.json` is fixed, sessions load the plugin without its hooks.
  - `Path not found: <path>. The runtime loader will report this as a load failure.`: fix the path or create the directory.
  - `Path contains ".." which could be a path traversal attempt: <path>`: use paths inside the root.
  - `Path is a file; skills entries must be directories containing SKILL.md`: point at the parent directory, or `.` for a root `SKILL.md`.
  - `No frontmatter block found` or `YAML frontmatter failed to parse: <error>`: add or fix the frontmatter between `---`. `No frontmatter block found` stops validation only with `--strict`.
  - `Plugin name "<name>" is reserved: it passes as one of Anthropic's own`: rename it for what it does.
  - `Unknown field '<key>'`: remove it or use the suggested name; ignored at load time; stops validation only with `--strict`. For directory listing fields such as `privacyPolicyUrl`, see the manifest reference.
  Other warnings, such as a missing description, are not listed. Fix each error and validate again until it prints none.
- **What `claude plugin validate <path> [--strict] [--json]` reads and how to read its result**:
  - Given a directory it validates `.claude-plugin/marketplace.json` if present, otherwise `.claude-plugin/plugin.json`, otherwise component files chosen by the directory's name (v2.1.233): a `skills`, `agents` or `commands` directory validates its files; a `.claude` directory validates those three inside it; any other directory validates those three under its `.claude`. With both manifests it validates the marketplace and the plugin (v2.1.289).
  - Symlinks are not followed: a linked `skills`, `agents` or `commands` directory under the plugin or `.claude` root is warned as unread; a linked entry inside one is skipped with a per-directory count; a named directory, or its parent `.claude`, that is itself a symlink is an error and nothing in it is checked. Name the real directory.
  - Not read: a `SKILL.md` at the plugin root; a `CLAUDE.md` at the plugin root is warned about; from a marketplace directory, the skill, agent, command, hook and MCP files of plugins listed in other directories. Validate each plugin directory to check those.
  - A manifest file not named `plugin.json` or `marketplace.json` and not in `.claude-plugin/` is validated as a marketplace when `plugins` is an array, when `plugins` and `owner` are both present, or when it has a marketplace-only field such as `owner` and no plugin-only field such as `author`; otherwise as a plugin manifest. Name the file to choose.
  - Exit `0` with `Validation passed` or `Validation passed with warnings`; `1` with `Validation failed` or `Validation failed (--strict treats warnings as errors)`; `2` with `Unexpected error during validation: <reason>`, when the validator itself failed (nothing on stdout, the message on stderr). `--strict` makes warnings such as unrecognized fields and missing metadata fail.
  - Observed on 2.1.325 (from `claude plugin validate --help` and its output; not yet on the docs pages): a hook under an unknown event is a warning, `hooks.<event>: unknown hook event; entry ignored at runtime`, and that hook's command is not checked further, so its quoting warning appears only after the event is fixed. The report ends with "Plugin directory checks" (README of at least 40 words, LICENSE or `license`, icon) that do not change the result unless `--profile directory` is passed.
  - `--json` (v2.1.259): `success`, `strict`, `target`, `manifest` (or `null`), `contents` (per file with something to report: `file`, `errors`, `warnings`, `notes`, and for mods `gatingHooks` with `module`, `pattern`, `hook`, `hasCatch`, v2.1.290), `advice` (v2.1.295). With both manifests, `manifest` is the marketplace result and `plugin.json` results go in `contents`.
  - An `Advice` block (`ℹ Advice (does not change the verdict):`, v2.1.295) means the README has no install line; it is neither error nor warning and never changes the verdict or exit code. Paste the suggested line into the named README and validate again. A suggested line with `<owner>/<repo>` does not clear it unchanged: validate the plugin's directory inside the marketplace, or fill in the real source; from a marketplace directory the source comes from the `origin` remote. An existing line counts when `plugin install` or `plugin i` is followed by `<plugin>@<marketplace>`, or by the name and `--marketplace <source>`.
- **`claude plugin init <name>` exits 1 without writing** (scaffolds `~/.claude/skills/<name>/`, alias `new`): an unknown `--with` value (valid: `skills`, `agents`, `hooks`, `mcp`, `lsp`, `output-style`, `channel`); an existing scaffold without `--force`; or the skills-dir source not allowed by managed settings (`Plugins from ~/.claude/skills/ are blocked ...`, B7). Success prints `Created plugin "<name>" at ~/.claude/skills/<name>`, the id it loads as and the `claude plugin disable` command; it validates what it wrote.
- **`claude plugin tag [path]` exits 1** with the reason when it cannot tag safely: no `version` in `plugin.json` or the marketplace entry, the tag already exists, or the working tree is dirty. It checks that `plugin.json` and the marketplace entry agree on the version before creating `<name>--v<version>`. Preview with `--dry-run`. If `--push` fails, the tag is still created locally and the command exits with an error.
- **`Plugin <name> has conflicting manifests: both plugin.json and marketplace entry specify components.`**: the entry sets `strict: false` and declares `commands`, `agents`, `skills`, `hooks`, `outputStyles` or `themes`. Remove those from the entry, or set `strict: true` so they are appended to `plugin.json`.
- **`Warning: No commands found in plugin <name> custom directory: <path>. Expected .md files or SKILL.md in subdirectories.`** (debug log only, nothing in the session or Errors tab): the `commands` path exists but holds no `.md` or `SKILL.md`. Add files or remove the path.

## Read the debug log

Many plugin causes are recorded only in the debug log: a `--plugin-dir` copy overriding an installed one, which hooks matched and their exit codes, an MCP or LSP server's startup error, a `.mcp.json` entry dropped for failing the schema, a commands path with no files. Sources: "CLI reference" (`--debug`, `--debug-file`), "Commands" (`/debug`), "Environment variables" (`DEBUG`, `CLAUDE_CODE_DEBUG_LOGS_DIR`, `CLAUDE_CODE_DEBUG_LOG_LEVEL`), "Hooks reference" and "Debug your configuration".

- `claude --debug` turns debug mode on and writes the log to `~/.claude/debug/<session-id>.txt`. It prints nothing to the terminal: open the file.
- `claude --debug='mcp,startup'` keeps only those categories; `--debug='!mcp'` excludes one. The filter applies only in the `=` form; `--debug mcp` with a space turns debug on without filtering. For an MCP server that starts but lists no tools, `claude --debug=mcp`, then read the server's stderr in the log.
- `claude --debug-file <path>` writes the log to a path you choose and turns debug mode on by itself. It takes precedence over `CLAUDE_CODE_DEBUG_LOGS_DIR`. Use it when you need to know where the file is, for example `claude --debug-file /tmp/claude-debug.log`, then search that file.
- `/debug [description]` inside a running session turns debug logging on from that point and has Claude read the log; anything before it was not captured.
- `DEBUG=1` in the environment is the same as `--debug`. `CLAUDE_CODE_DEBUG_LOGS_DIR` sets the log file path (a file, despite the name) and does not turn debug on by itself.
- `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` adds high-volume lines, such as hook matcher counts; `info`, `warn` or `error` reduce noise. Default `debug`.
- For a hook: start with `--debug` or `--debug-file`, trigger the event on purpose, and read which matchers matched and each hook's exit code. To check Setup and SessionStart hooks without a session, `claude --debug-file <path> --init-only`, then read the log.

## B6. Host a marketplace

For the marketplace owner.

- **Relative-path plugins fail in URL-based marketplaces**: installs fail with `its marketplace entry path does not stay inside the marketplace directory` and installed ones with `Plugin source path refused`, because a URL marketplace downloads only `marketplace.json`. Give each entry a fetchable source, e.g. `{ "name": "my-plugin", "source": { "source": "github", "repo": "owner/repo" } }`, or host the marketplace in a git repository so relative paths resolve.
- **A root plugin's git submodule is empty after install**: since v2.1.295 only submodules that hold plugin files are fetched, judged from paths written in the plugin's configuration and files (not paths a script builds at runtime). Write the path out, such as `${CLAUDE_PLUGIN_ROOT}/vendor/tool/run.sh` in a hook command; then every submodule is fetched for that plugin.
- **Marketplace validation errors** from `claude plugin validate .` in the marketplace folder (it also validates local-path entries and warns when an entry's `version` disagrees with the plugin's manifest; entry messages are prefixed `plugins[N] plugin.json →`):
  - Errors: `Duplicate plugin name "<name>" found in marketplace` (unique names); `Path contains "..": <path>` under `plugins[N].source` (no `..`); `Marketplace name cannot contain control or bidirectional-formatting characters` and the same for `Plugin name` (remove the character); `Claude Code cannot install plugins from marketplace "<name>". ...` and `Claude Code cannot install plugin "<name>". ...` (rename to the stated rule).
  - Warnings: `Marketplace has no plugins defined`; `No marketplace description provided`; `Plugin name "<name>" is not kebab-case` (the claude.ai sync requires lowercase, digits and hyphens); `Entry declares version "<a>" but <path>/plugin.json says "<b>"` (match `plugin.json`, which is authoritative at install); `Marketplace name "<name>" is reserved in Claude Desktop` (`org`, `org-provisioned`, `unknown` in any case); `Marketplace name "<name>" is not accepted by Claude Desktop` or the same for a plugin (at most 128 characters of letters, digits, `.`, `_`, `-`, starting with a letter or digit).
  - Before v2.1.247, control characters in a marketplace name were reported only as `Marketplace name impersonates an official Anthropic/Claude marketplace`.

## B7. Blocked by the organization

Each refusal names the managed setting behind it. The fix belongs to the administrator; tell the user which setting to ask about.

- **`Marketplace source '<source>' is blocked by enterprise policy`** (on add, update or install): `blockedMarketplaces` or `strictKnownMarketplaces`. `Allowed sources: <list>` means the allowlist; `No external marketplaces are allowed.` means an empty allowlist; a `Tip:` that the shorthand assumes github.com means the allowlist permits a host by name: re-add with the full URL, e.g. `git@your-git-host.com:owner/repo.git`. Ask the administrator to allow the source, or use an allowed one. An earlier-added marketplace stops refreshing too.
- **`Marketplace "<name>" is not in the allowed marketplace list`** or **`Marketplace "<name>" is blocked by enterprise policy`** (Errors tab, for a registered marketplace): the same settings apply at load time; guidance shows the allowed sources, `Contact your administrator to configure allowed marketplace sources`, or `This marketplace source is explicitly blocked by your administrator`.
- **`Plugin "<name>" is blocked by your organization's policy and cannot be installed`** (or `cannot be enabled`, or `... is from marketplace "<marketplace>", which is blocked ...`, or `... depends on "<dep>", which is blocked ...`): the plugin, its marketplace or a dependency is blocked. Ask which entry applies; a blocked dependency blocks the install until its marketplace is allowed.
- **`--plugin-dir is disabled by your organization's managed settings (disableSideloadFlags)`** with `Plugins, custom agents, and MCP servers can only be loaded from sources your administrator has approved.`: also covers `--plugin-url`, `--agents`, `--mcp-config`. Load from an approved marketplace or ask the administrator. Related: `--plugin-dir copy of "<name>" ignored: plugin is locked by managed settings`.
- **`Plugins from ~/.claude/skills/ are blocked by your organization's managed settings`** (from `claude plugin init` or `enable`): ask the administrator to add `{"source":"skills-dir"}` to `strictKnownMarketplaces` or remove it from `blockedMarketplaces`.
- **`Command-sourced plugins are disabled by your organization's managed settings`** with `The plugin was not installed or updated and its command was not run.`: `disableCommandPluginSources`, or `allowManagedHooksOnly` alone when that is unset. Ask whether it can be published from an allowed source type.
- **`Marketplace '<name>' is seed-managed (<dir>)`** on `claude plugin marketplace update <name>`: pre-populated through `CLAUDE_CODE_PLUGIN_SEED_DIR` and read-only; a bulk update skips it. Ask the seed image maintainer (see Seed containers and CI).
