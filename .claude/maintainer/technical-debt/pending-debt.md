# 🧾 Pending Debt

> [!NOTE]
> Unresolved technical or maintenance conditions that cannot be fixed now. Each one has evidence, an owner and a way out. Items that are fixed, no longer apply or are kept for good move to `closed-debt.md`.

## 🎯 Entry criteria

Add an item only when all of these hold:

- A specific condition is observable or backed by traceable evidence. No speculation.
- It has a real operational, security, reliability, compatibility or maintainability impact.
- It cannot be fixed now: it waits on a decision or a spend only the user or the project's owners can make, on access or an external party, or the risk is accepted on purpose.
- A concrete next action exists, or a concrete condition that triggers reassessment.
- No other active record tracks it, such as an open issue or an ADR follow-up.

> [!WARNING]
> Do not add improvement ideas, speculation or a copy of the backlog. A problem that can be fixed now gets fixed, not logged.

## 🔄 Record maintenance

| Action | When | Rule |
| --- | --- | --- |
| ➕ Append | A new condition appears | Search both ledgers for the same condition first. |
| ✏️ Update | Evidence, impact, owner or next action changes | Revise in place. Keep confirmed facts apart from inference. |
| ✅ Close | The condition is fixed, no longer applies, or the user decides to keep it for good | Move the entry to `closed-debt.md` with the same ID and an outcome: resolved, obsolete or accepted. Never just delete it. |

> [!IMPORTANT]
> An item leaves this ledger only after its closed entry exists, with the evidence its outcome needs.

### DEBT-007 — The workflows' actions can't move to a GitHub lockfile from a cloud session

| Field | Value |
| --- | --- |
| **Status** | 🟠 Blocked |
| **Category** | security |
| **Owner** | Nery Samuel Murillo |
| **Logged** | 2026-11-15 |

#### 🔎 Evidence

- **Confirmed facts:**
  - GitHub's "Secure use reference" (docs.github.com/en/actions/reference/security/secure-use, read 2026-11-15) says a workflow dependency lockfile "supersedes SHA pinning for repositories that adopt it". "Workflow dependency lockfiles" says `.github/workflows/actions.lock` is generated by `gh actions-lock`, records each action's commit and repository identity, and doesn't pin reusable-workflow calls.
  - `github/gh-actions-lock` (HEAD 90ae563, 2026-11-04) "Requires an authenticated `gh`" and reads the action repositories through the REST and GraphQL API (`internal/ghapi/`).
  - In this cloud session, `api.github.com` answers 403 "GitHub access to this repository is not enabled for this session" for repositories not attached to it, with the session token and with `GITHUB_PAT`. `add_repo` with `access: read` gives git reads only for a public repository. The cloud proxy also refuses GraphQL.
  - The workflows (`validate.yml`, `release.yml`, `claude.yml`, `claude-code-review.yml`, `evals.yml`, `.github/actions/setup`) pin every action by commit SHA with a `# vX.Y.Z` comment, as `.claude/rules/architecture/github.md` requires.
  - actionlint 1.7.12, the latest release on 2026-11-15, rejects the `$/` self-repository form that `gh actions-lock --migrate-local-actions` writes.
- **Inferences:** a lockfile run from the owner's machine should work, since `gh` is authenticated there; not tested.
- **Open questions:** whether zizmor 1.32.0 reads the lockfile, or flags version-tag references as unpinned.

#### 📈 Impact and next step

- **Impact / risk:** the workflows rely on SHA pins, GitHub's fallback, which don't cover the actions' own transitive dependencies or record the source repository's identity.
- **Why it is not fixed now:** generating the lockfile needs an authenticated `gh` with API access to the action repositories, which a cloud session doesn't have.
- **Next action:** on the owner's machine, run `gh extension install github/gh-actions-lock`, rewrite each `uses:` as its full version tag, run `gh actions-lock --ignore-local-actions` (keeping `./` while actionlint rejects `$/`), check `npm run lint:workflows`, add `gh actions-lock --verify` to Validate, and update the pin rule in `.claude/rules/architecture/github.md`.
- **Review condition:** a session with an authenticated `gh` on github.com, or an actionlint release that accepts `$/`.
- **Related records:** none.

### DEBT-008 — python-lsp-intelligence reports "basedpyright passed" for a file basedpyright never analyzed

| Field | Value |
| --- | --- |
| **Status** | 🟡 Pending |
| **Category** | quality |
| **Owner** | Nery Samuel Murillo |
| **Logged** | 2026-11-15 |

#### 🔎 Evidence

- **Confirmed facts:**
  - `plugins/python-lsp-intelligence/hooks/check.py` 0.3.4, `check_file`, runs `basedpyright -p <nearest config> <file>` and reads only the exit code: 0 is recorded as a pass. It never checks how many files basedpyright analyzed.
  - basedpyright 1.40.2 excludes `**/.*` (hidden folders) by default, and the docs ("Config files", `exclude`) say the defaults take precedence over `include`. A file under a hidden folder, below the folder that holds the config, is skipped even when passed by name: basedpyright prints "0 errors" and exits 0.
  - Reproduced on 2026-11-15 in an isolated copy of `HEAD` (commit `6a75534`): with a deliberate `return "not an int"` in a function typed `-> int` in `.claude/hooks/guard-quality-gates.py`, the hook printed `"python-lsp-intelligence: ruff check, ruff format, basedpyright passed"` and exited 0. With a `.claude/pyrightconfig.json` present, the same input exited 2 and listed 38 errors.
  - The guard committed at `HEAD` carries those 38 basedpyright errors under `typeCheckingMode` "all"; the hook never reported them.
  - The plugin's tests (`plugins/python-lsp-intelligence/tests/test_check.py`) have no case for a file basedpyright skips.
- **Inferences:** the same false pass hits any user's Python file under a hidden folder (`.github/`, `.devcontainer/`, `.claude/hooks/`) or under an `exclude` entry, so the plugin's promise to type-check every Python file Claude edits fails silently there.
- **Open questions:** whether `bash-lsp-intelligence` and the TypeScript plugins also read "nothing checked" as a pass.

#### 📈 Impact and next step

- **Impact / risk:** type errors in those files ship unreported, both in this repository and on third-party users' machines, while the hook tells Claude the file passed.
- **Why it is not fixed now:** the owner chose on 2026-11-15 to record it and fix it in a later change, after the current Python configuration work.
- **Next action:** in `plugins/python-lsp-intelligence`, write a failing test first (a file with a type error under a hidden folder must give exit 2), then run basedpyright with `--outputjson` in `check_file`, and report a file whose `summary.filesAnalyzed` is 0 as not checked (exit 2), with the fix to apply (give that folder its own configuration). Update the README and CHANGELOG, and release it as 0.3.5 through `plugin-releases`. Then check the sibling LSP plugins for the same pattern.
- **Review condition:** the 0.3.5 release, or any change to `check_file`.
- **Related records:** none.
