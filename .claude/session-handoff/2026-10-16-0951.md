## Decisions

- Plugin changes go through a PR, but Claude does not open one on its own: opening needs a push, and pushes of plugin changes need the user's approval; pushes outside plugins/ are authorized
- A plugin's version bump happens inside its PR, and the release is verified right after the merge: a tag created before the merge would point at a commit that main (squash merges) does not contain; a separate release commit pushed to main was rejected
- The version-bump check runs at push, not at commit: the bump happens once per release, and a commit-time block would force one bump per commit
- Hooks that guard the flow must be standalone (bash and git only): the user does not want hooks that depend on third-party tooling such as Node
- Gates run per file after editing and in full before each push; the full list lives only in QUALITY_GATE, not in CLAUDE.md: one source per rule
- Files inside a skill are linked relative to SKILL.md, files outside it with `${CLAUDE_PROJECT_DIR}`, and a reference never links to another reference: the docs ask for references one level deep and Claude resolves relative links itself
- Memory is `MEMORY.md` plus one topic file per fact; decisions and technical debt do not go to memory but to the records under `.claude/maintainer/`
- Rules are tracked in git again so skills and cloud sessions can see them
- A branch of unmerged work was backed up as a zip of the plugin folder only, then deleted: the user chose to keep only the plugin

## Learnings

- A project skill named `verify` makes Claude Code run it before each commit; deleting it removes that automatic run (Claude Code Docs, Skills, "Run your checks before each commit")
- The `if` filter of a hook is best effort and still runs the hook on Bash input with `$()`, so the script must check the command itself (Claude Code Docs, Hooks, "How if patterns match Bash commands"; seen in this session)
- In a PreToolUse hook, `additionalContext` arrives with the tool result, so only a `deny` can act before a command (Claude Code Docs, Hooks, PreToolUse decision control)
- Hooks in `settings.json` reload without restarting; hooks from a plugin need `/reload-plugins` (Claude Code Docs, Hooks and Settings; seen in this session)
- Rules without `paths` load at launch; rules with `paths` load when Claude reads, writes or edits a matching file, and a name search does not count; Explore and Plan agents start without CLAUDE.md (Claude Code Docs, Memory and Subagents)
- Claude Code does not resolve Markdown links; the model does, relative to the file that holds the link (test with a small agent that opened `../assets/pending-debt.md` correctly)
- Skills synced from claude.ai do not get `${CLAUDE_PROJECT_DIR}` substituted; a plugin is copied to the cache and files outside it are not copied (Claude Code Docs, Skills and Plugins loading)
- Plugin updates leave the previous version in the cache for 14 days; most official marketplace plugins have no `version` and use the commit SHA (Claude Code Docs, Plugins loading; local cache listing)
- The plugin README version badge is dynamic and reads plugin.json from main, so no sync script is needed (shields.io returned 0.1.0 for session-handoff, equal to origin/main)
- Agents inside a plugin ignore `hooks`, `mcpServers`, `permissionMode` and `initialPrompt`; teammates ignore `skills:` (Claude Code Docs, Plugins components and Agent teams)
- `markdownlint` here requires compact tables and asterisk emphasis, which made the template tables of the original project-records skill fail (markdownlint-cli2 run on rendered templates)
- Run with the global `@types` as `--typeRoots`, `tsc` on `.github/scripts` reports about 247 real strict-typing errors; without it, the typescript6 plugin hook fails with TS2688 because no `@types/node` resolves
